# aperas

A local-first knowledge graph, worked through a CLI and a small webapp — nodes and
the links between them are the source; any `.md` file you see is a projection, never
something to hand-edit.

Source, issues and the full documentation: <https://github.com/bixycler/Aperas>.

## Install

```
npm install -g aperas
```

Needs Node.js 22 or later (the package declares it in `engines`). The package has no other
dependency; it puts one command, `aperas`, on your `PATH`. `aperas --version` prints the version
installed.

## Start a new graph

```
mkdir my-graph && cd my-graph
aperas init
aperas serve
```

`aperas init` creates the files a graph needs: `aperas.config.json`, an empty
`Apeiron/` store, and an `artifacts/` tree. `aperas serve` starts (or reuses) the
graph's service and prints a `http://127.0.0.1:<port>` URL — open it in a browser
to read and edit the graph.

Put Markdown files under `artifacts/`, then bring them in:

```
aperas track notes.md
aperas ingest
aperas tree notes.md
```

## Where the graph lives

A "graph" is a directory containing:

- `aperas.config.json` — `{ "name": "...", "graph": { "apeiron": "./Apeiron", "artifacts": "./artifacts" } }`
- `Apeiron/` — the graph's own on-disk store (the mirror: JSON-LD files, one per kind of node,
  meant to be committed to git)
- `artifacts/` — Markdown projections of the graph, regenerated by the tooling

`aperas service start` (and `aperas serve`, which starts the service if none is running) binds the
service to a graph for its whole life. The graph is the one named by `APERAS_APEIRON_ROOT` and
`APERAS_ARTIFACTS_ROOT` if they are set, else by the nearest `aperas.config.json` found by walking up
from the directory you run the command in. Run `aperas service start`, `restart` or `serve` where no
graph is found and it refuses, creating nothing: the message gives the path it resolved and how it
found it, and says to run `aperas init` first.

## The service

One service holds the graph in memory and every `aperas` command talks to it; only the service writes
the mirror. It exits by itself after 30 idle minutes, flushing what it holds.

```
aperas service start      # start it, bound to the graph of the current directory (a no-op if running)
aperas service stop       # flush and stop
aperas service restart    # stop, then start again, rebinding to the graph of the current directory
aperas service status     # look only: starts, stops and clears nothing
```

To use a different graph, `cd` into it and `aperas service restart`.

`aperas service status` prints one of four states, with the pid, uptime, port, the two roots, the
run directory, the version and the fingerprint of the code the service runs (it says when the code on
disk is newer, and that `aperas service restart` picks it up). The exit status tells the state:
`ready` 0, `starting` 1, `busy` 1 (the process lives and does not answer), `stopped` 3. `--json`
prints the same as one line.

The service refuses to start when it could not read the whole mirror (an id carried by more than one
document, or a document the engine refused); the text of the command names at most 20 of the ids and
their count, and the log, `service.log` in the run directory, names all the files and ids. `aperas service start --start-anyway` accepts the load and works
on the unaffected parts, copying every document it skipped to `<file>.rejected-<stamp>.json` first. The
run directory is `$XDG_RUNTIME_DIR/aperas`, or `aperas-<uid>` under the system's temporary directory.
The webapp listens on port 2736; `APERAS_HTTP_PORT` changes it.

A graph written by 0.2.x or earlier has a mirror in an older format that the service refuses. It needs
the one-time migration described in the `CHANGELOG.md` that ships with the package, with the two
Python 3 scripts of the repository's `monorepo/scripts/` (<https://github.com/bixycler/Aperas>).

## Working the graph with an agent

The CLI alone doesn't teach an agent the discipline this graph needs — that a
`.md` file is a projection never edited by hand, that dense linking and deep
read/write matter, and the sharper edge cases around updating list items. That's
what the bundled skills encode:

```
aperas skill install
```

Copies `aperas`, its three role skills and `kg-doc-ingest` into `./.claude/skills/` (or
`~/.claude/skills/` with `--global`) so an agent working in this project picks up the discipline
automatically. Pass `--host <name>` for a different agent host's own convention —
`claude` (default), `agents` (Antigravity), `codex`, `cursor`, or `opencode` —
installing to that host's own `.<name>/skills/` instead.

## Commands

`aperas --help` lists every verb (`init`, `skill`, `track`, `ingest`, `insert`,
`update`, `remove`, `tree`, `unfold`, `backlinks`, `serve`, `service`, ...); each
has its own `aperas <verb> --help`. `aperas --version` (or `-v`) prints the version.
